# Decision 0004 — Project Brief, Program, and MP3 Score Contract

- Status: accepted direction; MVP program-category and mapping-report slices
  implemented; full brief and ten-dimension schemas pending
- Date: 2026-08-26
- Decision owner: user
- Career-value tags: V1, V3, V4

## Decision summary

The first pipeline will use:

- a generated project brief containing site and scale;
- a pluggable brief provider with deterministic random and local-LLM options;
- a lightweight program constitution based on architectural heuristics, common sense,
  and explicitly scoped legacy rules;
- MP3 as the music input format;
- ten shared dimensions in the full architectural-score schema;
- confidence, provenance, and extraction-method metadata for every inferred music
  dimension.

In a real project, the generated-brief provider can be replaced by an external project
brief provider without changing downstream compiler contracts.

## 1. Pluggable project-brief provider

The downstream pipeline must consume one normalized `project_brief` contract. It must
not depend on how the brief was created.

```text
RandomBriefProvider(seed) ─────┐
                              ├─→ raw brief → normalize → validate → project_brief.json
LocalLLMBriefProvider(model) ──┤
                              │
ExternalProjectBriefProvider ─┘  (future real-project input)
```

### Required provider interface

Conceptually, each provider must support:

```text
generate(request, seed) -> raw_brief
normalize(raw_brief)    -> project_brief
validate(project_brief) -> validation_report
```

The implementation language and class names may change, but the provider boundary
must remain explicit.

### Normalized brief responsibilities

The normalized brief should eventually contain:

- brief ID and schema version;
- selected or requested typology;
- site boundary and units;
- target gross area range;
- floor-count or height range;
- occupancy/capacity range;
- contextual assumptions used by the experiment;
- requested program priorities;
- delivery constraints relevant to the prototype;
- provider provenance;
- generation seed;
- validation status and warnings.

### Provenance requirements

Record at least:

- `provider_type`: `random`, `local_llm`, or `external`;
- random seed;
- local model identifier when applicable;
- prompt/template version when applicable;
- generation timestamp;
- raw-response hash or artifact reference;
- normalizer and schema versions;
- validation warnings and repairs.

Random generation must be deterministic for a fixed configuration and seed. Local-LLM
output must pass the same normalization and validation path. Downstream modules should
never parse unrestricted LLM prose directly.

## 2. Site and scale generation

For exploratory runs, site and scale may be generated by seeded rules or drawn by a
local Ollama model. Generated values must stay within configured ranges and pass basic
geometric and program-capacity checks.

The first implementation may begin with simple site representations such as a
rectangle or a valid planar polygon. The generator should separate:

- configurable allowed ranges;
- random/LLM proposal;
- normalized site geometry;
- validation and repair;
- accepted project brief.

The site module should remain replaceable by a real survey/site input later.

## 3. Lightweight program constitution

The MVP program constitution combines:

1. typology-specific required spaces and relationships;
2. basic architectural heuristics and common-sense circulation rules;
3. selected legacy constraints that have been reviewed and re-scoped;
4. explicit warnings for checks that the project does not implement.

The immediate target is a plausible model without major programmatic, circulation, or
geometric errors. The MVP must not claim complete code compliance.

The executable expansion is defined in
[`docs/guidelines/program_constitution_guideline.md`](../guidelines/program_constitution_guideline.md).
It separates broad visual category from detailed room type, access class, and
jurisdiction-specific occupancy use; defines base-building and typology starter space
sets; and specifies the contracts and validation gates for restrooms, service spaces,
egress, accessibility, adjacency, vertical stacking, and program–structure negotiation.
Where this decision and the guideline differ in detail, this accepted decision controls
project scope while the guideline controls the current program-rule implementation
contract.

### Implemented MVP category slice

The first compiled pavilion model assigns every occupied mass to one explicit category:

- `public`: gallery volumes;
- `private`: service volume;
- `circulation`: entry volume.

The compiler validates that all three categories are represented. Blender preserves the
assignment on colored program massing and derived facade/structure objects, and the web
viewer can isolate each category. This is a schematic program-classification layer; it
does not yet resolve room-level access control, egress, accessibility, or code-required
occupant separation.

### Rule classification

Every rule should declare:

- rule ID;
- source and source type;
- applicable typology and scope;
- severity: `hard`, `soft`, or `advisory`;
- measurable condition;
- repair policy, if any;
- limitation or professional check reserved for later.

Suggested semantics:

- `hard`: the generator must reject or repair the result;
- `soft`: the generator may trade it against other objectives and report the tradeoff;
- `advisory`: reported for review without blocking generation.

### Legacy constraint references

Legacy repository (expected as a sibling directory):

```text
../architecture_automation_pipeline
```

Relevant sources:

| Source | Existing assumptions worth studying | Migration caution |
|---|---|---|
| `program_generator/OpenAI_ProgramDetails.py` | 18 × 33 m site, 80–90% programmed area, dimensions in 2 m increments, 14 m max width, 24 m max length, continuous 4 m × 24–30 m circulation spine | Values are tied to the wearable scanning/fabrication brief and cannot become universal defaults |
| `program_generator/EllipseAgent.py` | boundary containment, overlap avoidance, adjacency attraction, vertical alignment, iterative relaxation | Program relationships are embedded in code and must move to data/configuration |
| `Blender/structural_generator.py` | 6 m grid, 12 m retained-span check, public-space column avoidance, cores, slabs, beams, bracing, stairs/elevator | Core locations, CLT/glulam assumptions, program names, and paths are project-specific |
| `Blender/LOGIC.md` | pipeline inputs/outputs, collection ownership, constructability and explainer contracts | Documentation describes the legacy building and must be re-scoped per migrated capability |

These sources are heuristic references. Each reused rule must be copied into a new
typology/config contract with provenance and a deliberate applicability decision.

## 4. MP3 input contract

MP3 is the primary music input. MIDI and MusicXML are not required for the first
pipeline.

```text
MP3 file
   ↓
decode and normalize audio
   ↓
segment and extract observable features
   ↓
music_features.json
   ↓
interpret shared dimensions with confidence
   ↓
architectural_score.json
```

### Required audio provenance

Record:

- source file name and content hash;
- duration, channel count, decoded sample rate, and normalization method;
- analysis-window and segment settings;
- extractor/model names and versions;
- feature confidence or reliability status;
- manual annotations or overrides;
- generated artifacts and timestamps.

The original MP3 remains an input asset. Downstream building modules should consume
normalized feature and score data, not reopen and reinterpret the audio independently.

### Reliability rule

Some dimensions are directly measurable from mixed audio; others require inference,
source separation, transcription, classification, or manual review. The schema must
allow:

- `observed`, `inferred`, `model_assisted`, or `manual` extraction methods;
- confidence values;
- `unknown` or unsupported values;
- alternative hypotheses when useful;
- user-approved overrides without deleting the original extraction.

Low-confidence musical claims must not silently control high-impact architectural
decisions.

## 5. Shared architectural-score dimensions

The full schema contains these ten dimensions.

| ID | Shared dimension | Music proposes | Architecture negotiates |
|---|---|---|---|
| 1 | Genre / Style（音乐种类） | Macro genre convention such as classical, jazz, electronic, or industrial | Proposes an architectural language/grammar from the approved library |
| 2 | Hierarchy（层级） | Melody and accompaniment relationships | Primary, secondary, and service-space topology |
| 3 | Repetition（重复） | Motif or ostinato recurrence | Bays, standard modules, or repeated program units |
| 4 | Variation（变奏） | Development and transformation of a theme | Rule-based changes in module size, facade opening, or component angle |
| 5 | Density（密度） | Note-onset density and rhythmic compactness | Density of structural members, spatial divisions, or facade elements |
| 6 | Continuity（连续） | Legato and smooth transition | Continuous paths, surface development, or visual connection |
| 7 | Interruption（中断） | Rests, caesurae, or voice interruption | Courtyard, void, threshold, or deliberate break |
| 8 | Polyphony（复调） | Multiple independent, interwoven voices | Parallel building systems such as structure, circulation, and facade |
| 9 | Tension / Release（张力） | Dissonance, buildup, and resolution | Compression/opening, dark/light, and low/high spatial contrast |
| 10 | Tempo of Change（变化频率） | BPM and rate of musical-feature change | Frequency of architectural-parameter and spatial-sequence changes |

`Tempo of Change` refers to rate of change over time. It should not be confused with
audio spectral frequency.

## 6. Genre-to-style boundary

Genre may propose one or more architectural grammars or grammar weights. The accepted
grammar must remain explicit and traceable. Typology, tectonics, site, and validation
may reject or limit the proposal.

Two experiment modes are required to preserve causal clarity:

### Mode A — Fixed grammar

Hold typology, tectonics, and style grammar constant while changing music. This tests
whether hierarchy, repetition, variation, density, continuity, interruption,
polyphony, tension/release, and tempo of change produce controlled differences.

### Mode B — Genre-conditioned grammar

Allow genre classification to propose a grammar from the approved candidate library,
then record the proposal, compatibility checks, accepted grammar, and any human
override. This tests the pluggable interpretation layer.

Mode A should be established first because it produces cleaner evidence that music
changes composition independently of style selection.

## 7. Full schema versus first extractor

All ten dimensions belong in the architectural-score schema from the beginning. The
first MP3 extractor does not need to claim equal reliability or full automation for all
ten.

The initial implementation should choose a small end-to-end subset with reliable
audio features and keep the remaining dimensions as optional or reviewable fields.
Candidate early dimensions include density, tempo of change, interruption, dynamics
within tension/release, and repetition. Genre, hierarchy, variation, and polyphony may
initially require model assistance or manual verification.

An unsupported dimension should remain `unknown`; it should not receive a fabricated
default that appears to come from the music.

## 8. Executed mapping report

Every completed building generation must produce a `mapping_report` assembled from
actual `BuildingElement.score_bindings`. Each entry records:

- measured music feature, value, unit, method, normalized value, and confidence;
- Shared Score dimension, value, interpretation method, confidence, and proposal;
- executed rule ID, direct/inverse direction, target parameter, and declared range;
- actual applied minimum/maximum, human-readable outcome, and negotiation note;
- affected element IDs, element kinds, and programs.

The report groups by actual `(rule_id, target_parameter)` pairs. One score rule may
therefore produce multiple report entries when typology-specific systems interpret it
differently. Planned rules without executed bindings do not count as translations.
Unsupported dimensions and known proxy limitations remain visible in the report.

## Consequences

- The first input pipeline is audio-based and requires decoding, segmentation, feature
  extraction, confidence, and provenance infrastructure.
- The brief source is replaceable and does not leak into downstream design modules.
- Local Ollama models may propose project briefs and assist selected music
  interpretations through explicit provider interfaces.
- Program rules begin as transparent, limited heuristics with declared scope.
- The score schema supports ten dimensions while MVP extraction remains staged.
- Controlled evidence separates score-driven changes from genre-driven grammar changes.

## Amendment 2026-08-30 — all ten dimensions are emitted, on unequal terms

The MVP observed four dimensions and left six unsupported, which meant six of the datum
set's variables were declared design fixtures and the music could not reach them.
`backend/app/audio.py` now measures eight further features and `backend/app/score.py`
emits all ten. Emitting them is not the same as claiming them equally.

| Dimension | Source feature | Method | Confidence |
|---|---|---|---:|
| `tempo_of_change` | `tempo_bpm` | observed | 0.82 |
| `tension_release` | `rms_energy` | observed | 0.95 |
| `density` | `onset_density_hz` | observed | 0.90 |
| `continuity` | `spectral_centroid_hz` | inferred | 0.72 |
| `repetition` | `chroma_recurrence` — a self-similarity matrix on chroma | observed | 0.78 |
| `variation` | `timbre_variation` — pairwise MFCC distance between segments | observed | 0.75 |
| `hierarchy` | `dynamic_range_db` — RMS 97th minus 5th percentile | observed | 0.80 |
| `interruption` | `novelty_peak_rate_per_min` — smoothed onset-novelty peaks | observed | 0.74 |
| `polyphony` | `spectral_contrast_db` + `harmonic_ratio` | **inferred** | 0.55 |
| `genre_style` | flatness + zero-crossing + centroid + harmonic share | **inferred** | 0.35 |

Three rules keep this honest.

**Repetition and variation must not share a source.** Repetition asks whether material
returns; variation asks how far it travels between sections. They are different
measurements, and giving them one feature would have been a way of appearing to support
two dimensions while supporting one.

**A proxy is declared as a proxy.** `polyphony` is inferred from spectral contrast and
harmonic share; nothing in this project counts voices. `genre_style` is worse: genre
classification from raw audio is a trained-model problem and there is no model. What is
measurable is a **timbral position** — bright and percussive against dark and sustained —
so that is what is emitted, and its architectural proposal is a facade-grammar
*weighting* a human accepts. It never selects a grammar and is never presented as a
genre.

**Confidence clamps travel.** `datums.py` scales how much of its declared range a datum
may cross by `confidence / 0.75`. A dimension at 0.35 confidence moves its datum only
47 % of the way from the midpoint to either end, so a weak reading nudges the design and
a strong one commits. Without this, a timbral guess would swing an envelope from fully
glazed to largely solid with the same authority as a measured dynamic range, and the
mapping report would be a fiction.

**A missing feature still produces a shortened score.** An artifact recorded before the
extended extractor has the four original metrics and `None` for the rest; `score.py`
emits four dimensions, and the datum layer records `provenance='design_fixture'` for
everything downstream. Nothing is padded with invented values.
